# Agent 适用性判断

从业务任务需要什么判断出发，选择能满足目标且容易验证的执行方式。允许一条业务链路组合多种方式，不必把整个产品归类为同一种 Agent。

## 分解实际任务

依据现有流程列出输入、判断、工具操作、等待和完成条件。标明哪些步骤已有确定规则，哪些需要理解自然语言，哪些需要根据中间结果重新规划。

区分“用户表达不规范”和“任务执行路径不确定”：前者可能只需抽取或检索，不能单独证明需要一个自主规划的 Agent。

## 比较实现形态

| 形态 | 适用特征 | 需要确认的边界 |
| --- | --- | --- |
| 规则或普通功能 | 输入与决策规则稳定，可直接校验 | 异常与规则冲突如何处理 |
| 模型助手 | 需要语义理解或生成，主要决定仍由用户作出 | 输出依据、纠错与确认位置 |
| 固定工作流 | 顺序和分支可枚举，需要调用工具或跨时等待 | 持久状态、重试、版本和恢复 |
| 动态 Agent | 路径难以预先穷举，需要按反馈选择下一步工具 | 终止条件、操作范围、预算及接管方式 |

不要仅凭步骤数量、是否调用多个工具或使用向量库来认定一个系统需要动态 Agent。也不要把用户已经确定的产品目标替换成更容易实现的演示。

## 对每个环节给出取舍

说明采用该形态的业务理由、实际依赖与失败成本。检查：

- 工具返回是否足以校验结果，还是模型只能自我判断。
- 外部动作是否可撤销；错误是否会变成报价、订单或权限变更。
- 是否需要等待客户或其他岗位；恢复执行时原始条件是否仍有效。
- 人工接管时，是否能拿到已完成步骤、证据、当前版本和待决定的问题。

权限校验、价格来源、审批约束等明确规则应由可检查的业务机制执行。模型可帮助理解和整理，不能把“理解了规则”当成规则已被执行。

## 输出建议

交付一份按业务环节组织的方案，注明推荐形态、原因、所需工具、验证方法与剩余不确定性。只有方案竞争会影响选择时才展开比较，不必凑多个平行方案。

建议试验时，选择能区分两种方案的代表样本，并检查质量、人工介入、耗时与执行成本。样本和结果不足时保留未知，不写收益承诺。
