# AI Coding 任务交接

让开发者或编程 Agent 能看出需要改变什么、哪些业务条件不能破坏，以及怎样判断完成。优先整理现有产品决策，避免凭空扩展成新的系统。

## 先核实当前实现

有仓库时读取适用的项目说明，并定位与功能相关的页面、接口、服务、数据结构及已有验证。文件路径、接口名称和现有字段须以实际材料为准。

没有仓库时可交付实现无关的行为契约，不伪造“需要修改的现有文件”。业务决定尚未明确时，指出会阻止实现的具体选择，其余内容继续整理。

## 把用户动作连到业务结果

对每个有状态的动作说明：

`谁在什么前提下操作 → 输入与校验 → 调用或处理 → 保存的结果 → 用户反馈 → 异常出口`

UI 需要的数据应能追到真实来源；保存或执行动作应能追到实际服务。明确结果是模型建议、员工采用还是商业执行，避免一个“确认”按钮同时承担不同责任。

按当前功能需要检查：重复提交、版本变化、断线与重试、并发修改、旧异步结果返回。写清行为与验收条件即可；技术方案应结合现有系统，不强制引入框架或基础设施。

## 形成适量的开发任务

围绕可以独立验证的结果拆分工作，给出必要依赖和执行顺序。每项任务包括：

- 要解决的问题与交付范围。
- 已确认的相关文件或模块。
- 页面、接口及数据变化；不需要的层明确说明理由。
- 需要保留的业务约束和失败处理。
- 正常路径及有业务意义的异常验收。

需要修改持久化、权限或集成时，将相应后端和数据工作纳入同一交接。不能以静态演示、提示消息或前端内存更新替代实际保存。

## 验收与交付说明

验收检查实际产生的结果，包括必要的接口响应、保存数据与业务状态。采用已有测试和代表样本；额外测试应针对业务风险，避免只复述实现细节。

请求仅为交接文档时交付任务包；用户已经要求实现时，交接内容服务于继续实施，不增加一次不必要的确认。任何外部动作仍沿用当前任务的授权边界。

交付时区分已验证行为、未运行的检查和仍需业务确认的事项。可以参考 [候选采用功能的构造交接示例](references/example.md)。
