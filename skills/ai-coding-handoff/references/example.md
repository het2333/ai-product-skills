# Commexa：采用候选商品的构造交接示例

此例只描述行为契约，没有声称某个现有接口或数据库字段已经存在。实际交接应先替换为仓库中核实过的名称。

## 目标

员工比较原始需求与候选后，确认商品、数量和单位。刷新页面后仍能看到本次采用结果，不会因为重复提交新增重复业务行。

## 输入和前提

- 已存在的需求行标识与当前需求版本。
- 员工选择的商品标识、确认数量及单位。
- 当前操作人身份。
- 请求标识，用于关联重试及返回结果。

商品必须来自本次允许选择的范围；数量和单位通过业务校验。缺数量时展示需要补充的信息，不默认为 1。

## 建议行为

1. 页面提交时展示进行中状态，保留用户已修改的字段。
2. 服务端核对身份、需求行、版本和候选适用条件，再保存采用结果。
3. 相同操作的重试返回已有结果或等价状态，不产生重复采用记录。
4. 需求已被修改时拒绝基于旧版本的提交，返回可用于重新核对的信息。
5. 保存成功后，页面使用返回的当前状态更新；网络失败时允许查询是否已经保存，避免把响应丢失等同于没有执行。

## 验收样本

| 场景 | 可观察的通过条件 |
| --- | --- |
| 正常采用 | 返回已保存状态，刷新后商品、数量和单位一致 |
| 快速重复操作 | 没有重复业务记录，页面能解释当前状态 |
| 采用前需求改版 | 旧版本请求被拒绝，员工可重新查看原文与候选 |
| 返回响应中断 | 可以恢复查询结果，不要求盲目再创建一次 |
| 非法商品或数量 | 没有写入采用记录，原输入仍可修正 |

采用商品不自动等于核价、审批、发送或下单。这些后续行为在其各自流程中执行。
